# Architecture

The expansion uses room protocol 2 and a separate `CampaignRoom`. Shared `missions.ts` defines the fifteen authored trials and versioned eligibility; `campaign.ts` owns objective interactions, seeded puzzles, mounts, monsters, honor and mission outcomes. `presentation.ts` defines projection and inverse projection used by input and rendering. The active Phaser renderer is `iso.ts`; the previous flat renderer remains in the repository as reference. The camera follows the local predicted actor and reprojects cursor aim through its current zoom/scroll.

Campaign rooms fill companions after two seconds; rated legacy rooms retain their five-second matchmaking window. Campaign checkpoints are separate from competitive statistics. Campaign checkpoints use the same async persistence adapter as results: SQLite locally, Supabase Postgres in production. Migrations 003/004 add the private runtime schema and evidence cleanup; migration 005 adds private chat persistence; existing installations must not rerun 001. See [campaign details](CAMPAIGN.md) and [deployment steps](DEPLOYMENT.md).

The React application owns navigation, identity, persistent records and HUD overlays. Phaser owns battlefield drawing, keyboard/pointer input and movement prediction. Its game bundle is loaded when an arena opens. Cosmetic portraits are independent from server-assigned squad roles.

Colyseus accepts strictly validated input commands. A fixed 1/30-second accumulator advances the shared simulation; snapshots are broadcast every second tick. Each input has a monotonic sequence number. The browser discards acknowledged prediction commands and reapplies outstanding movement inputs to each authoritative snapshot. Remote actors interpolate toward snapshots. The server alone decides collision, damage, deaths, zone ownership, puzzle progress and encounter transitions. Clients cannot submit victory or progression records.

Rooms provide a five-second human matchmaking window, then fill empty seats with server bots. Duels have two seats, conquest eight, quests four. One squad occupies each team in conquest; quest rooms are isolated by squad ID. A disconnected participant becomes a bot during the 30-second reconnection grace period. Training uses a stationary dummy. Bots send input through the same movement and damage rules as people; demo enemies have slower reactions.

SQLite WAL is the local authority and durable queue. One transaction inserts a unique result, participant links, progression, badges and an attestation outbox entry. Completed results contain canonical sorted-key JSON and Keccak-256 hashes. Snapshot positions are never written every tick. Significant events are stored in result metadata; history shows a timeline. This is not deterministic full-match replay.

Production Supabase Postgres is authoritative through a private transaction-pooler connection (four connections; prepared statements disabled). The game_runtime schema preserves canonical player IDs and separately links auth IDs. Existing public tables remain legacy records; there is no production mirror queue. A transaction-scoped advisory lock serializes authoritative read/modify/write operations. SQLite uses an async transaction queue with AsyncLocalStorage so unrelated requests cannot interleave inside a transaction. Result acknowledgment follows commit; failed settlements retry outside the simulation tick. Render memory contains active rooms only. Owner configuration is required for live hosted acceptance.

Wallet binding uses an expiring single-use challenge signed by the wallet owner. Guest IDs are not wallet identities. No custodial player keys are created. Attestation is independent from combat; the optional Base Sepolia worker submits trusted hashes only when explicitly enabled, retries failures and checks existing anchors before resubmission. Demo records always retain simulated status. ERC-1155 issuance is supported and tested in the contract; gameplay inventory currently remains off-chain.

Version 3 results snapshot participant names and wallet/profile/AI identities at finish. Later wallet linking does not rewrite history. An AI substitute retains the disconnected player's profile identity. Shared result helpers preserve legacy version 1/2 hashing and winner digests. Authenticated participants can fetch `/api/results/:id/proof`; the browser recomputes the result hash and, for real records, independently reads the configured Base Sepolia contract through the public network endpoint. It checks result and winner digests and distinguishes simulated, unconfigured, missing, conflicting and unavailable records. The outbox verifies local integrity again before submission.

Private team text chat now uses Socket.IO independently of gameplay. The client authenticates with its signed game-session token and squad ID. The server validates current membership, chooses `team:<squadId>`, derives the sender name, and persists messages through the shared SQLite/Postgres adapter. A unique `(squad_id,player_id,client_id)` key deduplicates retries across reconnects/restarts. The last 100 messages are restored on connection. Membership/session checks precede broadcasts, including revocation for users who have switched teams. `SharedGameTransport` routes WebSocket upgrades to either Colyseus or Socket.IO on the same HTTP port; Engine.IO does not destroy unrelated upgrades. A single React chat component persists across page changes and portals into the team screen or the current fullscreen arena. Phaser disables keyboard capture and sends neutral actions while chat/text controls have focus. Competitive ready-up remains in the Colyseus squad lobby; legacy lobby-chat handlers remain for compatibility.

The Royal Gathering requires four hosted human identities, a consented private upload and four account approvals. File signatures, MIME types, size and squad membership are checked. Photos are never hashed into public result payloads or put on-chain; fellowship metadata hashes use pseudonymous member digests. Approved members can delete the image. This is social participation attestation, not biometric or physical-location verification.

Demo accounts, rooms, results, leaderboards and badges are explicitly partitioned. Only the demo endpoint accepts simulated gathering approvals. Normal progression cannot use it. Reset creates a new demo identity and leaves historical authoritative records intact.
